# Agent Brief: MKV Chapter & Media Info Backup Web App

You are building a full Dockerized web application to backup and restore MKV chapter data and track metadata (mediainfo) for an anime library. The app will run in Docker, expose a web UI, and operate on library folders mounted into the container.

## Goal

Create a web application that:

- Scans mounted library folders for MKV files.
- Extracts and stores:
  - Embedded chapters (as XML).
  - Track metadata (languages, track names, types, etc.) using `mkvmerge --info` or `mediainfo`.
- Stores everything in a SQLite database.
- Provides a web UI to:
  - Select a whole library or a specific show to backup.
  - Select a whole library or a specific show to restore.
  - Browse shows → seasons → episodes in a list view.
  - View chapter data and track metadata per episode in the UI.
- Does **not** hash files; matching is done by filename only.
- Is designed to be developed with Claude Code (you).

Assume filenames are stable (e.g., generated by TinyMediaManager), so `(show, filename)` is a sufficient key.

## Functional Requirements

### 1. Library & Show Model

- Libraries are top-level directories under `/libraries`.
  - Example: `/libraries/Anime`, `/libraries/Anime2`.
- A “show” is a subdirectory under a library:
  - Example: `/libraries/Anime/Some Anime Show`.
- Episodes are MKV files inside show folders (possibly with season subfolders).
  - Example:
    - `/libraries/Anime/Some Anime Show/Season 01/Some Anime Show - S01E01.mkv`
    - `/libraries/Anime/Some Anime Show/Some Anime Show S01E01.mkv`

The UI should:

- List all libraries under `/libraries`.
- For each library, list shows (direct subdirectories containing `.mkv` files, directly or recursively).
- For each show, allow:
  - Backup all episodes in that show.
  - Restore all episodes in that show.
- Optionally allow:
  - Backup all shows in a library.
  - Restore all shows in a library.

### 2. Data to Store

For each MKV file, store:

1. **Chapters**
   - Extracted via: `mkvextract chapters <file>` → XML string.
   - Stored as text in the DB.

2. **Track Metadata (MediaInfo)**
   - Use either:
     - `mkvmerge --info <file>` (JSON) or
     - `mediainfo --Output=JSON <file>`.
   - You must store enough info to later:
     - See track type (video, audio, subtitles).
     - See language.
     - See track name/title.
     - See default/forced flags if available.
   - Store as JSON text in the DB.

You do **not** need to store the whole media file info, just what’s needed to restore track metadata conceptually. For now, focus on:

- Per track:
  - `track_id` (as reported by mkvmerge/mediainfo)
  - `track_type` (audio/video/subtitle)
  - `language`
  - `name` / `title`
  - `default` (bool)
  - `forced` (bool)
  - any other useful flags you can easily parse.

Store this as a JSON array of tracks in the DB.

### 3. Database Schema

Use SQLite with SQLAlchemy.

Core tables:

#### `libraries`

- `id` (PK)
- `name` (unique) – e.g. `"Anime"` (derived from directory name)
- `path` – absolute path inside container, e.g. `/libraries/Anime`

#### `shows`

- `id` (PK)
- `library_id` (FK → libraries.id)
- `name` – show folder name, e.g. `"Some Anime Show"`
- `path` – absolute path inside container, e.g. `/libraries/Anime/Some Anime Show`
- Unique constraint: `(library_id, name)`

#### `episodes`

- `id` (PK)
- `show_id` (FK → shows.id)
- `filename` – filename only, e.g. `Some Anime Show - S01E01.mkv`
- `path` – full path inside container
- `season` – optional string/number if you parse it (can be nullable)
- `episode` – optional string/number if you parse it (can be nullable)
- Unique constraint: `(show_id, filename)`

#### `chapters`

- `id` (PK)
- `episode_id` (FK → episodes.id)
- `chapter_xml` – full XML text from `mkvextract chapters`
- Unique constraint: `episode_id`
- Optional: `created_at`, `updated_at`

#### `track_metadata`

- `id` (PK)
- `episode_id` (FK → episodes.id)
- `tracks_json` – JSON array of track objects (see above)
- Unique constraint: `episode_id`
- Optional: `created_at`, `updated_at`

You may add timestamps (`created_at`, `updated_at`) to tables as you see fit.

### 4. Backend API

Implement a FastAPI app with endpoints like:

#### Libraries

- `GET /api/libraries`
  - Returns list of libraries found under `/libraries`.
  - For each: `id`, `name`, `path`.

#### Shows

- `GET /api/libraries/{library_id}/shows`
  - Returns list of shows in that library.
  - For each: `id`, `name`, `path`, maybe episode count.

#### Episodes

- `GET /api/shows/{show_id}/episodes`
  - Returns list of episodes for a show.
  - For each: `id`, `filename`, `path`, `season`, `episode`, and maybe flags:
    - `has_chapters`
    - `has_track_metadata`

- `GET /api/episodes/{episode_id}`
  - Returns detailed info for one episode:
    - Basic fields.
    - Chapters (XML or parsed structure).
    - Track metadata (JSON).

#### Backup Operations

- `POST /api/shows/{show_id}/backup`
  - Triggers backup for all episodes in a show.
  - For each MKV:
    - Extract chapters via `mkvextract`.
    - Extract track metadata via `mkvmerge --info` or `mediainfo`.
    - Insert/update `episodes`, `chapters`, `track_metadata`.
  - Returns a job ID or immediate result (you can start simple: synchronous).

- `POST /api/libraries/{library_id}/backup`
  - Same but for all shows in a library.

#### Restore Operations

- `POST /api/shows/{show_id}/restore`
  - For each episode in the show:
    - If the file exists on disk at the recorded `path` (or same filename under the show folder), re-embed chapters.
    - Use `mkvmerge` to create a new file with chapters (and optionally re-apply track metadata if you implement that later).
    - For now, restoring chapters is sufficient; track metadata restore can be a future extension.
  - You can implement as:
    - Create `episode.mkv.tmp` with chapters.
    - Replace original file safely.

- `POST /api/libraries/{library_id}/restore`
  - Same but for all shows in a library.

You can start with synchronous operations (blocking HTTP calls) and later add a simple background job system if needed.

### 5. Web UI

Build a simple but usable UI:

#### Layout

- Header:
  - Title: “MKV Chapter & Media Info Backup”.
  - Maybe a small status line.

- Main view:
  - List of libraries.
  - For selected library:

#### Features

- **Library view**
  - Show all libraries.
  - Buttons per library:
    - “Backup all shows”
    - “Restore all shows”

- **Show view**
  - When a show is expanded/selected:
    - Show basic info (name, path).
    - Buttons:
      - “Backup this show”
      - “Restore this show”
    - List episodes, ideally grouped by season:
      - Season headings (e.g. “Season 1”).
      - Under each season, list episodes:
        - Filename.
        - Icons/flags indicating:
          - Chapters backed up?
          - Track metadata backed up?
        - Click to open episode detail.

- **Episode detail**
  - Modal or separate page.
  - Show:
    - Filename, path.
    - Chapters:
      - Either raw XML in a `<pre>` block or a simple parsed list (chapter name + timecode).
    - Track metadata:
      - Table of tracks:
        - Type, language, name, default, forced, etc.
  - Buttons:
    - “Backup this episode” (if you want per-episode backup).
    - “Restore chapters for this episode”.

- **Operations feedback**
  - For backup/restore actions:
    - Show a simple progress indicator or log.
    - At minimum, show a success/error message when done.

You can keep the UI simple but clear. Focus on:

- Clear navigation: Library → Show → Episodes → Episode detail.
- Clear actions: Backup / Restore at library, show, and episode levels.
- Visibility of stored data: chapters and track metadata.
